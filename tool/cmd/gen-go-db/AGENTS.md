# gen-go-db 工作规则

本文件约束 `tool/cmd/gen-go-db` 目录内的所有开发工作。规则硬约束，不可违反；项目规则不得违反公司级规则（见仓库根目录 AGENTS.md）。

## MUST（硬约束，不可违反）

### 1. 禁止直接修改目录下的代码

- 禁止在未经过任何流程的情况下，直接修改本目录下（含子目录）的任何代码文件。
- 本目录是代码生成工具，改动可能影响大量下游项目的生成结果，必须把改动当作"影响面未知"来处理。
- 唯一的例外是：用户在当前会话中明确、逐项批准过的改动。

### 2. 必须遵循「分析 → 解决方案 → 用户确认」机制

任何改动都必须按以下三步顺序执行，缺一不可：

1. **分析（Analysis）**：先做完整的分析，不跳过、不凭印象。
   - 必须包含 **代码调用链路分析**：从入口（main/子命令）到目标函数，说明数据如何流转、哪些文件/函数会被调用、改动的影响面。
   - 必须包含 **对现有 dao 实现逻辑的分析**：说明当前 `dao/` 下的实现（生成器、解析器、模板等）是如何工作的，改动点落在哪个环节，为什么这样改是对的。
2. **解决方案（Solution）**：给出明确的方案，说明改什么、为什么、影响哪些文件与行为。
3. **用户确认（Confirmation）**：将分析与方案呈现给用户，**获得用户明确确认后才可动手**；用户不同意则不得修改。

### 3. 新增数据库操作 dao 的测试规则

- 新增的数据库操作相关 dao 测试，文件**必须放在本目录的 `test/` 目录下**，禁止散落在其他目录或新建临时的测试目录。
- 测试必须**充分列举所有测试场景**，至少覆盖：
  - 正常路径（happy path）
  - 边界条件（空值、零值、主键边界、超长/超短输入等）
  - 异常与错误路径（非法输入、未找到、类型不匹配、数据库错误等）
  - 特殊输入（需要忽略的零值列、自定义规则、命名 SQL 等工具特有行为）
- **禁止简单测试**：不允许只测一条 happy path、不允许断言不充分的占位测试、不允许为了"有测试"而写的表面测试。测试通过的标准是"场景覆盖充分 + 断言可验证行为"。

## 流程管理

- 涉及代码改动的工作，一律先完成「分析」并展示给用户，进入「用户确认」前不得产生任何代码变更。
- 校验（编译、`go test` 等）通过是改动可交付的基本前提，需在改动完成后实际运行验证，不能用"应该没问题"代替。
